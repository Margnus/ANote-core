# OBJ05顺序计划接入原authority的设计

2026-10-30，基线9ca9f47。现行计划允许C–F不连接生产的业务规则/设计；本文不放行预览UI、生产存储或架构冻结。原OBJ05的置顶/置底、文件互通与背景不可选保持；原子history及幂等是既有文档authority约束，不能以纯计划替代。基线时只有ObjectOrderRules和6项共同测试；以下为原接入条件，文末记录本轮实现范围。

## 为什么不能直接保存计划

SceneSnapshot.reordered是同revision的只读组合工具，不能提供业务提交。MemoryDocumentAuthority当前只在state赋值处发布root/journal/history；DocumentDelta的beforePositions/afterPositions仅记录新增或删除成员，undo位置恢复也只处理新恢复成员。纯顺序变化没有ObjectChange，用现有逻辑会丢失顺序undo。不能把顺序伪装成删除重建或几何Transform：那会改变身份/对象epoch、计费、dirty语义和引用责任。

源码依据：[原delta](../shared-core/src/commonMain/kotlin/dev/notecore/document/DocumentDelta.kt)、[原authority](../shared-core/src/commonMain/kotlin/dev/notecore/document/MemoryDocumentAuthority.kt)、[原组合工具](../canvas-core/src/commonMain/kotlin/dev/notecore/canvas/prototype/Scene.kt)。这些观察绑定9ca9f47；不是平台执行结论。

## 接入选择

| 原责任 | 拟接入方式 | 不可省略的拒绝/恢复 |
|---|---|---|
| 单一命令及journal | 在原DocumentCommand族表达documentId/baseRevision/operationId、pageId、选中身份与FRONT/BACK；输入集合复制，payload重试身份明确。只在测试/模型接入，暂不增加预览UI | 同op同payload返回原receipt；同op不同payload拒绝；非法/无变化不耗journal或身份 |
| 同一排序规则 | 原authority校验身份/版本/预算后复用ObjectOrderRules，不复制另一套排序实现；最大对象数来自其原budget | 旧root、缺页、混页、缺失/重复/非法身份全拒绝，不部分重排 |
| 同一发布点 | 原空对象变化的metadata barrier推进scene/root revision，再按计划重排；目标page contentRevision同步推进 | 只改顺序，不改对象身份/样本/几何或对象epoch，其他页顺序槽位保持；不得发布同revision的新顺序 |
| 原稀疏history | 在原DocumentDelta增加仅目标页的显式before/after对象顺序信息，普通命令保持原membership恢复路径 | undo/redo先检查当前页成员与预期顺序，再恢复目标顺序；不匹配返回HISTORY_CONFLICT，不能静默覆盖 |
| 原journal/history/活体额度 | journal计入复制的选择身份；delta两侧顺序数组/身份逻辑收费，projectedCharge在完整scene/root复制前包含同一公式 | 预算差1字节拒绝且root/journal/history/身份不变；不可先复制未计费的全场景顺序再称分配前准入。逻辑收费不等于heap |
| 原文件和渲染 | 继续使用现有v2的对象迭代顺序；实际业务命令成功后才可捕获保存，page/root版本使派生缓存失效 | 不改文件版本；fixture往返仅表达验证，不证明App导出/实际跨端产品支持 |

顺序history只记录本次受影响页，不把完整root或另一个可变scene留在history；不得为了排序增加第二个authority、队列或长期缓存。页外对象的全局槽位规则沿原计划，在undo/redo时仍须满足同一成员集合前提。旧owner退休/新owner接管、生产资源pin/正式SQLite继续遵循原门禁，没有新增替代验收。

## 必须执行的验证

1. 原authority一次排序后root/page版本各按既有约定变化，样本/身份/对象epoch不变；其他页槽位与两组相对顺序稳定。
2. 同命令重试/同ID异payload、旧root、混页、坏身份、空/重复选择、无变化、已退休owner逐项拒绝，拒绝前后状态一致。
3. 排序→新增/删除/变换→逐步undo/redo，检查顺序及原membership位置恢复，不只测试排序一次往返。
4. 精确journal/history预算与差1字节反例；undo/redo与新编辑清redo、history驱逐均保持原策略，不能漏掉顺序数组收费。
5. 原codec往返顺序、原ledger同版本fork拒绝继续保留；完成命令只得MEMORY_ONLY receipt，不能显示已保存。
6. 受影响共同/Native及实际双端消费者分别绑定来源；公开API/预览UI/生产存储若未接，不标这些验收通过。物理M-1/C1与全部113条保持。

采用此接入路径，拒绝同revision组合、删除重建排序和独立排序authority。下一实现应直接扩原命令/delta/发布流程及上述反例；本文不计为这些代码或平台已经完成，也不新增一个通用PoC阶段。

## 2026-10-30实际接入结论

已按上述路径接入internal OrderObjects、原MemoryDocumentAuthority唯一发布点和DocumentDelta.PageObjectOrder稀疏身份顺序。journal收费复制选择身份；history投影/实际两侧收费相同；规划前以原inputBytes检查512+全局对象数×256+选择身份费×4的临时逻辑上限，复用LIVE_BYTE_CAPACITY拒绝。该上限不是实测heap，也不是生产输入并发预留。原public UI入口未扩展。

新增6项共同测试/JVM571项通过，覆盖版本与对象epoch/载荷保持、混合成员/变换历史反复往返、原幂等与整笔拒绝、精确及少1字节三类预算、驱逐/清redo、精确页成员顺序匹配、v2及ledger新版本接纳。见[绑定报告](../reports/object-order-atomic/report.json)。HISTORY_CONFLICT的顺序匹配用内部稀疏delta直接反例验证，原authority在任何发布前调用它；未伪造第二authority注入fork。Native/实际双端消费未验，物理/C1/OBJ05全部验收保持。

采用原模型接入并保留原门禁；下一步核验新候选Native编译/共同语义，再沿既定双端消费者范围推进，不以此内部模型测试宣布层级UI或完整OBJ05交付。
