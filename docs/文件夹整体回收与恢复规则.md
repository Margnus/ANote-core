# 文件夹整体回收与恢复规则

2026-11-10，用户明确选择“整棵子目录及其中笔记一起进入回收站，支持整体恢复”。对应 LIB-03/LIB-08，延续现行计划允许的非生产业务规则；不是生产元数据或普通 App 功能交付。

## 唯一事务的操作范围

复用原 `LibraryTrashSnapshot`，其中活动目录/笔记位置、原笔记回收行和新增文件夹回收组属于同一完整空间版本。`LibraryFolderTrashRules` 不持有可编辑状态、不分配文档 ID、不访问正文或文件。所有 before/after 行必须由未来唯一元数据事务共同校验、共同提交，推进一次元数据版本；不能逐行调用删除接口。

整组回收包括选中目录、所有活动后代目录和位于其中的活动笔记，保留目录 ID、父子关系、名称、noteId、原目录及同一次删除时间。已经单独进入回收站的笔记不被重新归组或改写删除时间；无关目录、活动笔记和既有回收条目保持。空目录树也形成回收组，不能因笔记数量为零而遗漏。

笔记仍保存在原 trash 行中，`folderGroupId` 显式指向回收组；组保存目录行及成员 noteId，没有第二份正文。两侧成员关系、原目录及删除时间须完全一致。漏组、漏成员、重复成员、未知成员、活动/回收身份冲突、坏目录树全部拒绝，不能过滤坏行后继续。组内笔记单独调用原 restore 返回 `GROUPED_NOTE`；UI 后续应引导整体恢复，不拆散组。

## 整体恢复与冲突

恢复复用所有原身份，移回完整目录树和笔记位置，再移除对应 trash 行及组。原父目录仍在活动目录中时恢复到原位置；已不存在时仅将组根恢复到资料库根，其后代关系保持。同名新目录不会替代原父目录，目录 ID 不可复用的原约束继续适用。

恢复必须满足现有五级深度限制。若原父目录后来移动到深层导致整组超深，则整批拒绝 `DEPTH_LIMIT`，保留回收组，用户可先调整父目录后重试；不静默裁掉后代或改为恢复一部分。活动身份碰撞视为损坏快照拒绝。跨空间、旧版本、不完整枚举、坏组及超候选容量均不产生计划。容量按活动加回收目录合计 10000、活动加回收笔记合计 100000 检查，只是候选规则准入，不是生产 heap 或分页性能上限。

清空仍走原 inspect/confirm/plan 两步，确认范围现在同时包含原 note 行和按稳定身份排序的完整文件夹组。UI 必须展示目录树/笔记范围及影响，不能只展示 `rows.size`，也不能把没有笔记的回收组当成空回收站。任一组、成员、目录字段、时间或空间版本变化令旧确认失效。移除这些元数据引用不授予正文/资源文件删除权，历史、冲突、任务、读者 pin 与原 GC 保护保持。

## 验证和接入出口

共同测试覆盖嵌套回收/恢复的身份及无关数据保持、原父目录消失回根、深度溢出整批拒绝、组内单笔拒绝、空组清空范围、坏组/遗漏/碰撞、完整性/版本/空间和聚合容量。测试中的 apply 只是核对计划的内存投影，不能证明 SQLite 原子性或耐久保存。原 Android library-test 复用同一批共同测试及原单笔回收/批量规则；各平台结果以本轮报告为准。

采用此用户选定策略及 internal 规则，下一接入是 DEV-041 前置满足后的正式元数据事务/opId 重试、编辑中回收协调、双端目录/回收站及确认 UI、关闭重开、资源保留与实际故障恢复。M-1/C1/生产门禁保持，LIB-03/LIB-08 仍为部分实现/待验收；没有把整体规则当作完整产品删除流程。
