# 文本对象原链路接入设计（未冻结）

2026-11-09，OBJ-01/OBJ-02/DATA-03 的后续原对象增量。依据[文本内容与IME提交边界](文本内容与IME提交边界.md)、原 ADR-0013/0014、现行 C1 与模块方向。当前只落实接入设计，不批准提前切生产存储、扩普通预览能力或冻结 SDK。

## 当前缺口与采用路线

当前 `canvas-core` 的 SceneSnapshot 条目、ObjectChange、CanvasCommand 和原 authority 都围绕 StrokeObject；`shared-core` 的 DocumentRoot 在同一 scene 上组合页面/标题/历史。TextPayloadDraft 只是 shared-core 内部校验候选，没有进入 scene/codec/命令或 App。不能将“有一个文本值”解释为已有可保存文本对象。

采用原 SceneSnapshot 的对象族升级路线：同一个有序对象表、同一对象 ID/epoch、同一 authority 发布点，文本作为其中的对象种类。拒绝在 DocumentRoot 外另存一份可编辑文本表、另建文本 authority，或只让渲染器保存 attributed string。宿主 IME 的未提交草稿不是已提交对象，也不能成为第二持久正文。

这是接入方向决定，不是现阶段源码已升级。真实混排实现仍须依 C1/DEV-041 前置与完整对象能力一起交付；下述步骤不拆成无限独立旁路模型。

## 模块方向与模型

1. 原规范对象族留在 `canvas-core/commonMain`。引入与现有 ID/layer/epoch/transform 一致的对象协议，再由原 StrokeObject 和新文本对象实现；SceneSnapshot、ObjectChange、历史成员定位及顺序保持原单一有序容器。不得导入 Android/UIKit、DB、IME、字体系统或 shared-core。
2. 文本内容校验在该增量采用时随文本载荷迁到相同或更低的无平台模型层，并迁移现有6项约束测试。当前 shared-core 的 internal 候选不直接被 canvas-core 引用，也不复制为两套“规范”校验。共享的 Unicode 校验依赖须同步下移或保持明确委托，不能通过开放上层业务包绕过方向。
3. 文本对象拥有局部逻辑框、原字符/基本样式和稳定字体请求；规范资源引用按正式资源协议关联。草案 fontRequest 字符串不是已验证 ResourceKey/字体文件许可，不能直接充作已存在资源。字体解析与 fallback 结果属于带版本的派生布局。
4. 对象 transform 仍只表达几何变化，移动/旋转不改字符/runs。逻辑框 resize 是内容命令。读者可共享不可变载荷，不能用宿主可变 Spannable/NSAttributedString 或可写 runs 作为 scene 条目。

跨模块类型签名变化必须纳入原最小白名单/双端编译审查；不以一个新接口名暗示正式 SDK 冻结。具体对象协议签名与正式字体引用键仍随完整对象协议评审，本文不新增公开声明。

## 原子命令、历史和额度

- 新文本创建/替换在原命令族中携带 opId、document/scene/page/object 身份、base revision 与目标 epoch。原 journal 保持相同 payload 重试/异 payload 冲突语义，不能用宿主重发文字代替重放原命令。
- 替换前先完成 Unicode、完整样式范围、逻辑框和引用校验及正文/身份/journal/history/临时容器额度准入；成功仅在原唯一发布点替换一个不可变对象，并推进目标对象/页/root 的原版本。失败不能先改变字符再回补样式，不能修改选页或清 IME 草稿。
- 历史持有稀疏对象 before/after 与所需顺序/页身份，复用原 DocumentDelta/驱逐策略；旧、新文本载荷的实际保留责任进入原预算。候选 logicalByteCharge 不能直接宣称已包含资源 pin、布局/native 缓冲区或真实 heap。
- 变换/删除/复制与文本替换均通过原 authority。复制分配新 objectId，保留相对坐标并按正式资源协议共享有效引用；undo/redo 必须核对预期身份/epoch/成员/顺序，不逐项调用可半成功 CRUD。
- 新会话 open 不从旧 IME 选区或 glyph index 推断 command range。原 pen pending 恢复信封不自动支持文本草稿；需要恢复未提交文本时必须有显式版本和真实 IO 责任设计，不能塞进原 StrokeSamples 或假装现有文件已覆盖。

## 格式兼容和拒绝

文本首次进入规范内容时必须使用显式新对象/文件能力版本，旧 reader 对未知对象明确拒绝，不能过滤后返回“可编辑的笔迹部分”。当前 v1/v2 和恢复信封的有效数据保持原读取范围；混排 writer 不替换现有预览 writer，直到完整消费者和存储前置满足。

原 PreviewDocumentReader/Notebook 在未具备文本编辑/显示能力时，应在采用 owner 之前拒绝含文本的 scene。原 strokeCount/point 下标读取不能成为“忽略文本也算成功打开”的入口。只读结构检查、预览受限、完整编辑是不同能力结果；不能把 source asset 检查或新 codec 往返当成 App 支持。

未知版本、坏 Unicode/runs、字体引用缺失、预算不足与 IO 失败分别有可归因结果。拒绝保留源资源/文件及最后确认正文，不能靠静默替换字体、删字、裁边或降级为图后仍报告无损。

## 几何、布局、渲染与资源

文本的保守 bounds 从逻辑框经同一 transform 得到；空间索引/套索先按对象逻辑框候选，再按正式命中策略判断，不拿 glyph 数当字符索引。布局溢出必须可见，不能让未计入 bounds 的 glyph 任意外溢却声称命中/显示一致；最终边界策略须与导出共同验证。

布局身份至少绑定 objectId/epoch、逻辑框、文本/样式、字体解析结果和布局算法版本。视口/尺寸变更可重建派生布局，不改变规范字符。后台只消费不可变捕获值；迟到布局不得覆盖新对象，owner/资源 pin/结果交付责任复用原调度契约。

屏幕与导出消费同一规范载荷和明确的字体回退/溢出策略。字体源、face、授权/缺失与 native reader 生命周期由正式资源 port 负责，不让 kernel 打开文件或识别平台字体路径。当前 hasGlyph/Font 来源调查只证明有限平台能力，不等于该 port 已存在。

## 一个完整增量的验收出口

先完成同一链路的对象/codec/原子命令与 delta、bounds/index/hit-test、资源引用、屏幕和导出，再接双端 TextOverlayPort。需要可操作的用户闭环：新建文本→实际中英文 IME（含 emoji/组合字符）→选区/复制粘贴→字号/颜色/加粗→移动/缩放→undo/redo→保存/关闭/重开→缺字体现提示/导出核对；编辑期间同一手势不能同时成为笔迹。

同一增量覆盖旧 reader 拒绝混排、旧文件保持、目标删除/旧 epoch/坏范围/容量不足拒绝保草稿、只读、后台/尺寸/关闭交接，以及混合笔迹和文本的顺序/历史往返。对文件 IO、资源引用和实际双端操作分别绑定版本证据。未齐时只记已验证子范围，不晋升 OBJ-01/02 或放行生产门禁。

本路线采用后停止为同一文本候选增加相似字符串/字体 happy path。下一实现必须改变上述原对象链路的具体缺口；若 C1/正式资源前置未满足，继续明确保留该集成待验，不把本设计或 internal 校验包装为产品交付。
