## Android

调试签名预检候选已固定在 `d157418`，适合先检查安装及采集器的设备兼容性。下载后先核对 SHA-256，再用下面的采集器核对安装文件。正式 M-1 比较按各目标机型固定构建模式与签名。[CI APK 压缩包](https://github.com/Margnus/ANote-core/actions/runs/45606125574/artifacts/15017459491)。[源码和签名回执](../reports/android-m1-preview-20261125/verification.json)。

先明确 `ADB`、`SERIAL`、`APK` 为本轮工具、设备和签名候选；`RUN` 必须是新证据目录。安装并打开候选，开始前/结束后各留一次同进程快照。

```sh
mkdir -p "$RUN"
python3 tools/capture_android_m1.py --adb "$ADB" --serial "$SERIAL" --apk "$APK" --output "$RUN/pre"
"$ADB" -s "$SERIAL" shell perfetto --query > "$RUN/perfetto-sources.txt"
"$ADB" -s "$SERIAL" shell perfetto --txt -c - -o - \
  < tools/probes/m1-android-perfetto.pbtxt > "$RUN/interaction.pftrace" 2> "$RUN/perfetto.stderr"
python3 tools/capture_android_m1.py --adb "$ADB" --serial "$SERIAL" --apk "$APK" --output "$RUN/post"
```

录制时执行下面的工作负载，核对 pre/post PID、APK SHA、热状态和渲染后端。保留 FrameTimeline 有效范围、掉帧关系与 RSS 时间序列。点快照另提供 PSS 和可用的 GPU 分类。持续峰值需覆盖重叠时段，按设备可用工具补 PSS/GPU；缺信号显式记录。检查环形缓冲和事件丢失，丢失所需窗口时重录。旧设备缺 Perfetto/FrameTimeline 时保留错误，用系统 profiler/可用的 atrace、分段 framestats 和外部视频量测，按原方法记录实际覆盖范围。

### 重叠工作期间的有界点采样（2026-11-21）

可在另一终端与 Perfetto/录像并行运行以下诊断采集，覆盖书写、历史、翻页、保存与资源释放重叠窗口：

```sh
python3 tools/capture_android_m1.py --adb "$ADB" --serial "$SERIAL" --apk "$APK" \
  --sample-count 61 --interval-seconds 5 --output "$RUN/series"
```

默认仍为单次采集；采样数 1..3600、最小起点间隔 0.1..60 秒、请求时间跨度至多 3600 秒。每个点依次执行 ADB 命令并记录真实 UTC 与单调时间，慢命令会延后下一个点，不追赶补采，不把配置间隔当成实际采样频率。报告 `samples` 与 `sample-NNNN-*` 原始文件对应；单次采集保留原文件名。

每点核对唯一 PID 与 `/proc/PID/stat` 的 starttime，指标按 PID 请求并核对输出中的包名/PID；首尾核对安装路径及 APK 摘要。进程切换/复用、包变化、超时、中断或无法读取进程身份时保留已取得的原始文件和摘要，整份报告保持 incomplete。`/proc` 读取权限和 dumpsys 输出格式必须在目标设备上预检；不支持时如实保留失败，改用前述平台 profiler 方法，不绕过权限或降级身份核对。

这些仍是**离散、非同时取得的点快照**，不能据此声称连续峰值或总预算已验收。dumpsys 自身会产生扰动，需与不采样的控制运行比较；真实持续峰值、P95、帧和触笔延迟继续以目标设备原始 trace/视频及对应方法判断。采集器始终保持 `m1_accepted=false`、`physical_verified=false`。工具回归命令为 `python3 tools/verify_android_m1_capture.py`，其 fake ADB/虚拟时钟结果仅证明采集协议行为。

## iPad

准备对应候选的签名 iPhoneOS IPA，保留安装命令/签名标识、安装回执、构建编号和二进制摘要。设备通过 Developer Mode 和 Instruments 连接。用下列命令选定硬件 UDID 和预览进程 PID。

```sh
xcrun xctrace list devices
xcrun xctrace list templates
xcrun devicectl device info processes --device "$UDID" --search NoteCorePreview
python3 tools/capture_apple_m1.py --device "$UDID" --pid "$PID" --ipa "$IPA" \
  --template "$TEMPLATE" --seconds 310 --output "$RUN/interaction"
```

按本机列出的模板分别采集帧/呈现与 Allocations/VM/footprint，记录采样方法、符号化和 trace 原始 TOC。录制时执行相同工作负载，另存录像与采样时间关联。采集前核对 IPA 内含唯一的非空预览可执行文件，记录整包与包内可执行文件的 SHA-256。采集后重新核对整包摘要，变化时保留原始结果并记为采集未完成。采集器同时保留进程和安装清单，产物关联仍需核对安装日志和本轮构建标识。可在任意开发机运行 `python3 tools/verify_apple_m1_capture.py` 复验候选校验。用物理 footprint 独立报告，与 Android PSS/RSS 分开。最低 iOS 17 模拟器使用原 `tools/verify_sketch_ios_host.py` 的显式目标及原 App XCTest，保留 runtime、独立消费者/原 App 结果及其各自产物摘要。

## 采集和判断

1. 先用现有 S1/S2 ink 子集、S9 长笔和已验证的 20 万点信封做预检。固定同一时间线，标记 DOWN/UP、动态→静态呈现、释放、翻页、历史、导入/重开和保存确认。安排保存与读者未释放、历史和解码同时存在的窗口，并记录其前、峰、释放后，区分逻辑额度与物理驻留。
2. 原性能口径使用完整 S1/S2/S4/S5/S9。详见固定蓝图的《06-性能与验收》。对子集与当前 App 尚不支持的负载单列待验。冷/暖各至少 30 次；常用书写、翻页连续至少 5 分钟，报告超预算帧比例（目标 <1%，60 Hz 16.67 ms、120 Hz 8.33 ms）；分别报告 S1 内存 P95（≤250 MB）与 S2/S4 峰值（≤400 MB）。
3. 用高帧率相机同时拍笔尖和屏幕，每刷新档至少 200 个有效片段。保留视频帧率、接触帧和首个可见墨迹帧、预测误差及被排除片段和原因。报告 P50/P95/最大值和采样分辨率。120 Hz 档 P95≤25 ms，60 Hz 档 P95≤45 ms；App 内输入和呈现 trace 单列。
4. 抬笔→生产耐久回执目标 P95≤300 ms，冷热 IO 各档加总至少 1,000 笔；先记录预览文件回执诊断基线。对照接受对象数、字节摘要、重复恢复、新进程重开及原件存续，分别标记正常退出、进程强停和掉电。
5. 每条记录包含需求 ID、温度/时间、工作负载及产物 SHA、有效与异常样本数、P50/P95/最大值、原始 trace/录像位置和缺测原因。预检报告保持待真机评审。
