# LIB-03 文件夹业务规则

状态：内部共享规则已实现，JVM验证；普通App与生产元数据未接入，需求未验收。

## 交付卡

目标：创建、重命名、移动与空文件夹删除有统一、可恢复的拒绝结果；移动不能制造循环或超过五级的后代。依据：requirements.csv LIB-03（P0，验收依赖DATA-01），现行开发计划允许独立业务规则；Core起点fc61a82。保留M-1/C1及正式存储前置。

实现位于shared-core的internal LibraryFolderRules，不新增公开SDK、存储authority、线程或队列。验收采用完整目录/笔记位置快照，返回单行before/after及spaceId/expectedRevision，失败只返回具体原因；测试同时核对输入未变化。JVM通过后采纳为后续元数据事务的规则入口，不以此声称App已有文件夹管理。

## 已采用的边界

- 资料库根不计为文件夹；其直接子文件夹为第一级，最多五级。移动检查整个子树的最终深度，禁止移到自身或任一后代。
- ID为调用者已分配的不超过128个UTF-16单元的合法Unicode非空白字符串。名称非空白、不超过120个UTF-16单元、Unicode合法；保留原字符和空白，不隐式归一化、截断或合并同名文件夹。本轮长度限制是内部候选规则，正式UI/迁移仍需统一决策。
- 规划只接受同一空间、同一版本、明确完整的快照；拒绝重复ID、断链、循环、超深旧树和指向未知目录的笔记。分页结果、遗漏回收站/其它引用的视图不得标为完整。
- 空文件夹可删除；含子文件夹或笔记时明确NOT_EMPTY。没有递归删除、搬移笔记或清理文件的副作用。非空删除的用户策略及回收站关联在正式元数据集成时确定，不能把NOT_EMPTY称完整产品删除流程。
- 计划不是准入预留或提交回执。后续唯一元数据事务必须在同一space/revision上校验并原子应用；新子目录、新笔记位置或其它并发元数据变化必须推进版本，使旧删除/移动计划失效。计划不能绕过实际事务中的引用/GC保护。
- 记录只含不可变字段；调用者须在同一owner内提供调用期间稳定的列表。规则不持有列表，不支持并发修改。候选准入最多10000文件夹/100000笔记位置，拒绝超限；这不是万条分页性能、进程heap或生产总预算结论。

`verifyPrototype`运行新增10项LibraryFolderRulesTest，报告见[结果](../reports/library-folder-rules.json)。覆盖操作串、五/六级、子树深度、循环、空间/版本/完整性、非空删除、损坏图、Unicode、缺失身份及容量拒绝；旧快照与笔记身份保持。共同JVM总计457项XML零失败，canvas任务复用既有结果，shared任务本轮实际执行。可移植性和依赖检查通过。

本轮不改普通App或APK，不声明Android/Apple runtime、持久化、平台UI或整项LIB-03已验。下一接入顺序为DATA-01/DEV-041正式元数据事务→双端目录UI→创建/改名/移动/删除/关闭重开/并发失败回归。普通功能与耐久保存仍受现行门禁约束。
