## 三、执行与记录纪律

1. 每个颗粒度先在[当前开发状态](当前开发状态.md)写执行卡（目标/范围/验收/验证方法），完成后记录实际结论与证据。
2. 验证：相关 commonTest + `:shared-core` JVM 测试；涉及 canvas-core 改动时同时跑其 JVM 测试。不凭 JVM 结果宣称平台/设备通过。
3. 提交：实现→测试→修复→差异审查→提交推送（已授权）；提交信息说明行为与范围，附需求映射。
4. 蓝图同步：仅更新需求账本的 `remaining_work`/`implementation_evidence` 记录及计划文档；internal 规则不提升 `implementation_status`/`acceptance_status`（与 OBJ-05、PDF-05 既有口径一致）。
5. 遇以下情况中断并请求用户决策：需要开放 App 功能/格式、需要真机或设备操作、破坏性格式变更、与并行会话改动冲突。
6. 工作区有其他会话未提交改动时，保留并避开相关文件；提交前复核 git status 与 diff。

## 四、门禁决策项（需用户确认，不阻塞上述 internal 工作）

1. **预览链路产品开放策略**：E4/P4 等 App 接线是否允许在完整 C1 前以"预览功能、非生产验收"名义接入普通 App。现行规则 DEV-042 依赖生产保存/算法版本，若维持则 App 接线统一等 C1。
2. **C1 门禁拆分**：是否将完整 C1 拆为逻辑契约项（可离线收口）与物理设备项（真机补验、作为发布门禁），使生产 SQLite 接线提前启动。此为架构决策，须修订 ADR 后生效。
3. **真机采购**：M-1 采集包已就绪，设备到位即可执行；触笔/heap/断电耐久不可由模拟器替代。
