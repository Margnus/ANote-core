原独立Java消费者与新共同回归均复现：10笔×20000点、坐标-1.2345678901234567e-100、pressure=1.2345679e-20f、time=Long.MAX_VALUE，合法root能通过reader/Notebook采用（retained5603542字节），却因16M字符硬限制无法保存。修复后同一Java消费者输出17200730字符并成功；不改变点数、原始数值、canonical模型或v1/v2格式。

## 从既有格式推导边界

点行由ASCII前缀、两个有限Double、Float及非负Long构成。当前固定工具链按Double最多25字符、Float最多16字符、Long最多19字符及分隔符推导，点行预留96字节并实际检查。元数据行根据128-unit身份、120-unit标题、固定字段和转义规则推导，单行UTF8最多1024字节；writer直接计UTF8而非假设字符=字节。有效代理对按4字节，其余BMP至多3字节，控制字符转义不扩大该上界。

| 部分 | 保守上界 |
|---|---:|
| 正文头尾 | 2048 |
| 128页面行 | 128×1024 |
| 5000对象行 | 5000×1024 |
| 200000点行 | 200000×96 |
| 独立恢复头/重复元数据余量 | 8×1024 |
| 单个20000点pending payload余量 | 20000×96 |
| 合计字符边界MAX_CHARACTERS | 26381312 |

这是按原字段/点数限额计算的保守编码范围，包含额外恢复余量，不是允许正文变成220000点。原32MiB文件边界不变，codec逐行计UTF8，平台写入/导出也先检查实际UTF8总字节再打开目标输出；读取继续32MiB有限流。普通合法长数字样本>16M但在推导范围内，可以采用、编辑、保存、重开。超点数/单笔/对象/retained原限额仍拒绝。

[Kotlin/Native 2.2.21 NumberConverter源码](https://raw.githubusercontent.com/JetBrains/kotlin/v2.2.21/kotlin-native/runtime/src/main/kotlin/kotlin/native/internal/NumberConverter.kt)分别按Float/Double精度转换并在阈值外使用科学表示；这是当前固定工具链的来源核对。[Primitives声明](https://raw.githubusercontent.com/JetBrains/kotlin/v2.2.21/kotlin-native/runtime/src/main/kotlin/kotlin/Primitives.kt)明确表示格式可能变化。数值宽度上界是本次格式推导/测试约束，不承诺未来工具链或未验平台永久一致；升级需重验，当前Native/Swift实际构建仍待。

## 原worker和恢复责任

- Android/Swift写入、导出和读取都引用原codec的共享原语边界，移除各自16M硬编码；保留原atomic IO、唯一authority/ledger/worker/pool。新增边界accessor仍未冻结，不是稳定SDK放行。
- 最大读取费用沿原公式4096 + MAX_CHARACTERS×8 + 3×8MiB =236220416字节预留，替换旧160MiB固定预留。原256MiB worker总额度不变，忙碌时仍走原背压/责任保留。最保守正文编码费用加完整pending工作费用243074944字节也在该原额度内；这些是声明费用，不是实测heap/GC或物理门槛。
- 恢复信封采用前额外核对pending若提交后的对象数、总点数及codec retained费用。否则可能先恢复、重试提交出一个无法再编码的root。新增守卫拒绝这种不可能完成的信封，不降级只取base，不修改原文件或清空pending。
- 200000点、单笔20000点、5000对象、128页及8MiB retained限额均保持。完整C1/M-1、生产SQLite和正式格式仍未放行。老预览构建的16M读取限额可能拒绝新长文档，故不能声称旧安装包已支持该容量；旧v1/v2可读范围仍保留。
