# 资源文件与数据库联合提交恢复边界（隔离设计验证）

2026-10-27，沿蓝图05“文件与数据库联合提交”和现行计划的C–F独立业务样本推进DATA-04/05/08。本文件不选择生产schema，不连接App、预览文件或文档authority；不能据此放行C1或DEV-041。

## 当前采用的责任顺序

1. 先持久记录进行中导入任务的身份，再在任务独占staging写入；完整关闭、大小和hash校验前不创建可见Document。
2. 完整资源以不覆盖方式promote。在本机探针中使用同一临时卷上的hard link完成no-clobber创建，已存在同内容只复用，已存在但损坏则明确REPAIR_REQUIRED并保持原字节。该API只是主机反例方法，不批准移动端promote port、目录fsync或最终文件协议。
3. 同一SQLite事务写Resource元数据、Document引用、Operation身份与任务完成状态。只有该事务提交后，此样本的document查询才可见新记录；没有“先显示文档、再补资源”的半状态。
4. 回执丢失时先读Operation并验证文档/hash一致及实际资源完整性。相同操作只重放已提交结果；身份冲突拒绝；资源已坏不能仅因DB里有Operation就宣称成功。
5. promote后DB尚未提交时，完整资源可能存在而Resource表还没有行。进行中任务必须保留目标hash，恢复及GC不能只扫描Resource/Document表便判孤儿。探针证明恢复记录存在，未实现最终GC与导入写者互斥；扫描器仍必须完整枚举任务并在真正退休前重新协调。

## 实际边界与期望

| 子进程退出点 | 重新打开后的可见状态 | 责任与恢复 |
|---|---|---|
| staging半写 | 无Document/Operation；任务running；只有不完整stage | 不误promote或提交。重试使用另一次stage，原任务/源载荷保留。 |
| 完整stage已fsync/关闭 | 无Document/Operation；任务记录hash | 可重新校验并promote，未显示成功。 |
| promote完成 | 资源文件存在，Resource/Document/Operation尚不存在；任务running+hash | 任务持有恢复责任，不凭“无Resource行”回收。重试不覆盖完整资源。 |
| DB事务未提交 | 资源文件存在；实际进程退出后DB回滚到无Document/Operation | 保留任务及资源；相同操作重试提交一次。 |
| DB已提交但回执未返回 | Resource/Document/Operation各1，任务complete | 相同操作返回ALREADY_COMMITTED，无新stage/文档/操作。 |

另验证3条：预存在错误字节的hash地址拒绝覆盖且无文档可见；同一operation换文档拒绝且不stage；已提交后人为损坏测试资源，再次重放明确要求修复，数据库状态和损坏文件都不被悄悄重写。所有原source.bin载荷保持。这里的“可见”仅临时SQL查询，不是资料库UI或生产保存标记。
